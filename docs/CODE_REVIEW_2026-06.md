## 부록 A — 검증에서 기각된 항목 (거짓양성)

아래 항목은 도메인 리뷰에서 High/Critical로 보고됐으나, 독립 검증 에이전트가 실제 코드를 재확인한 결과 **실재하지 않거나 이미 방어되고 있어 기각**되었습니다. 거짓양성을 걸러낸 기록으로 남깁니다.

#### ~~getUserPosts가 소프트 삭제된 게시글까지 반환 (deletedAt 필터 누락)~~ — user · 원 심각도 High

- **위치** `src/main/java/com/jipsamoye/backend/domain/user/service/UserServiceImpl.java:103-106` · **축** 컨벤션
- **원 주장** petPostRepository.findAllByUser(user, PageRequest...)는 파생 쿼리로 deletedAt 조건이 없다(PetPostRepository.java:20). 그런데 PetPostRepository에는 softDeleteAllByUser(37-38: 'UPDATE PetPost ... SET deletedAt = CURRENT_TIMESTAMP')가 존재하므로 게시글은 소프트 삭제될 수 있고, 그 결과 삭제된 게시글이 유저 프로필 게시글 목록에 그대로 노출된다. soft delete 컨벤션(deletedAt != null = 삭제됨, 조회에서 제외)을 위반한다.
- **기각 사유** 기각. 주장은 PetPost 엔티티에 걸린 Hibernate 엔티티 레벨 소프트 삭제 필터를 놓쳤다. PetPost.java:24 에 `@SQLRestriction("deleted_at IS NULL")` 가 선언되어 있다(org.hibernate.annotations.SQLRestriction import, line 11). @SQLRestriction은 해당 엔티티에 대한 모든 SELECT/파생 쿼리 SQL에 자동으로 `AND deleted_at IS NULL` 조건을 append한다. 따라서: - UserServiceImpl.java:103-104 의 petPostRepository.findAllByUser(user, PageRequest...) 는 파생 쿼리이지만 Hibernate가 deleted_at IS NULL 을 자동 부가하므로 소프트 삭제된 게시글은 반환되지 않는다. 주장의 핵심 전제(deletedAt 조건 없음 → 삭제 게시글 노출)가 성립하지 않는다. - countByUser(user) (UserServiceImpl.java:40, 74) 역시 동일하게 @SQLRestriction의 영향을 받아 삭제 게시글을 제외하고 카운트한다. 제안된 "countByUser도 필터 검토" 역시 불필요. 소프트 삭제 쿼리(PetPostRepository.java:37 `UPDATE PetPost ... SET deletedAt=CURRENT_TIMESTAMP WHERE p.user=:user AND p.deletedAt IS NULL`)가 deletedAt 조건을 명시적으로 가진 이유는, JPQL 벌크 UPDATE 문은 @SQLRestriction이 적용되지 않기 때문에 개발자가 직접 넣어야 했던 것이다. 이는 오히려 SELECT 계열은 @SQLRestriction으로 일관 처리되고 있음을 방증한다. 즉 프레임워크(Hibernate)가 자동 보장하는 소프트 삭제 필터를 누락 문제로 오인한 케이스이며 동작상 문제 없음. 참고로 다른 도메인(예: petPost 목록 API)도 동일한 findAllBy... 파생 쿼리를 쓰면서 @SQLRestriction에 의존하고 있어, 이 방어 패턴은 프로젝트 전반의 의도된 설계다.

## 부록 B — 검토 방법 및 한계

- 각 도메인을 전담 에이전트가 `docs/CONVENTIONS.md`·`docs/ARCHITECTURE.md`·`docs/QUALITY.md`를 기준으로 리뷰했습니다.
- Critical/High 항목만 검증 단계를 거쳤습니다. Medium/Low는 1차 리뷰 결과이며 검증을 거치지 않았으므로 일부 거짓양성이 섞여 있을 수 있습니다.
- 정적 분석 기반이라 런타임 부하·실제 쿼리 플랜은 측정하지 않았습니다. N+1 등은 실제 트래픽·데이터량에 따라 영향도가 달라집니다.
- confidence(높음/보통/낮음)는 리뷰 에이전트의 자기 확신도이며, 낮음 항목은 정책 판단이 필요해 코드만으로 확정할 수 없는 경우입니다.
