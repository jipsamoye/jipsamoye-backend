# Figurine OpenAI Rate Limit 대응 아키텍처 비교 (핸드오프)

> 작성: 2026-08-02. AI 키캡 생성(figurine)의 OpenAI `gpt-image-1` **분당 5회 제한** 하에서
> **유저 100명이 동시에 요청해도 유실 없이 처리**하는 구조를 논의한 결과 정리.
> 코드 구현 전 단계 — 개념·동작 원리·장단점·결론만 담는다.

## 0. 전제: 어떤 아키텍처로도 안 되는 것

- **대기 시간**: 100건 ÷ 5건/분 = 마지막 유저는 최소 20분 대기. OpenAI 쪽 제한이라 불변.
  → 해법은 아키텍처가 아니라 (a) 대기 순번 UX(폴링 응답에 "n번째 대기 중"), (b) OpenAI Tier 승급뿐.
- **과금 폭주**: 큐는 유실을 막지 수요를 막지 않는다. 한 유저가 500건 넣으면 500건 과금.
  → 사용자별 쿼터(일일 N건 등)는 어떤 방식이든 앱 코드에 별도 구현 필요.
  (기존 `feature/figurine-cost-guard` 브랜치는 **폐기 결정** — 쿼터는 새로 구현해야 함)

## 1. 방식 0 — 현재 구조 (@Async 인메모리 큐)

**동작 원리**: `createJob`이 FigurineJob을 PENDING으로 DB 저장 후 `@Async("figurineExecutor")`
워커에 위임 → 워커(core 1, queue 20)가 S3 소스 다운로드 → OpenAI 블로킹 호출(30~120초)
→ 결과 S3 업로드 → COMPLETED 저장. 프론트는 2~3초 간격 폴링.

**한계**:
- 인메모리 큐 용량 20 → **21건째부터 거부**. 100명 수용 불가
- 재배포/재시작 시 **큐 대기분 증발** (PENDING 고아 행 → 5분 후 자가치유로 FAILED)
- **429 대응 코드 0줄** — 실패 즉시 FAILED, 유저 재시도 → 429 재발 루프
- 분당 5회를 인지하는 페이싱 없음 (core 1이 우연히 눌러주고 있을 뿐)
- 힙 384MB JVM 안에서 이미지 바이트(base64 ~4MB) 처리 + 2분 블로킹 스레드

## 2. 방식 1 — SQS + Lambda (큐 2개)

**개념**: 요청/응답 큐 2개를 두고 Lambda를 큐 소비자로. 상태(DB)는 계속 앱이 소유,
Lambda는 무상태 워커 — Lambda가 DB에 접근할 필요가 없어짐(EC2 위 Docker MySQL 개방 불필요).

**동작 원리**:
```
createJob: PENDING 저장 + 요청 큐(FIFO) send → 즉시 201
Lambda(SQS 트리거, 동시성 2): S3 다운로드 → OpenAI → S3 업로드 → 응답 큐 send
  실패(429) 시 throw → visibility timeout 후 SQS가 자동 재전달, 상한 초과 시 DLQ
앱 @SqsListener(응답 큐): jobId로 COMPLETED/FAILED 저장
```

**장점**:
- 접수 무제한 + 메시지가 서버 재시작과 무관하게 보존 (앱이 죽어도 Lambda는 계속 처리)
- **재시도가 공짜**: visibility timeout 재전달 + maxReceiveCount + DLQ가 SQS 기본 기능
- 앱에서 무거운 I/O·이미지 바이트 완전 제거
- 비용 0원 (SQS 월 100만 건 무료, Lambda 프리티어)

**단점**:
- 요청 경로가 5구간(앱→SQS→Lambda→SQS→앱)으로 늘어 **디버깅·로그 분산** (CloudWatch + 앱 로그)
- at-least-once → **중복 전달 = OpenAI 중복 과금** 리스크 → 요청 큐를 FIFO + 중복제거 ID(jobId)로 차단 필요
- 페이싱이 "동시성 2 × 호출 30~120초 ≈ 분당 1~4건"이라는 **근사** — 정밀 제어 아님
- 관리 포인트 증가: 큐 3개(요청/응답/DLQ) + IAM + 앱에 SQS 리스너 의존성, 로컬 테스트 어려움(LocalStack)
- 앱이 Lambda 시작 시점을 모름 → PROCESSING 상태 의미 약화, 자가치유 타임아웃 재설계 필요

## 3. 방식 2 — FigurineJob 테이블 + @Scheduled 디스패처 + Lambda 동기 invoke

**개념**: 이미 있는 FigurineJob 테이블을 **DB 기반 작업 큐**로 승격. 페이싱·재시도·클레임은
**내 코드**(앱)가 소유하고, 무거운 일(S3↔OpenAI)만 Lambda를 **원격 함수(RPC)**처럼 동기 호출.
큐 인프라 0개.

**동작 원리**:
```
createJob: PENDING 저장만 하고 즉시 201 (접수 상한 = DB 용량 = 사실상 무제한)
@Scheduled(12초 주기 = 분당 5건 페이싱):
  가장 오래된 PENDING 1건을 원자적 클레임 (UPDATE ... WHERE status='PENDING'
    — 블루-그린 전환 중 두 인스턴스가 떠도 한쪽만 성공, 이중 처리 방지)
  → Lambda 동기 invoke(jobId, sourceKey 전달) → Lambda가 S3→OpenAI→S3 처리, URL만 반환
  → COMPLETED 저장. 429 응답이면 PENDING 복귀 + retry_count 증가(상한 초과 시 FAILED)
대기 순번: COUNT(PENDING AND createdAt < 내것) — 폴링 응답에 포함
```

**장점**:
- **정확한 분당 페이싱** (방식 1의 근사보다 정밀), 재시도 정책도 코드로 직접 제어
- 큐 인프라 0개 — 한 레포에서 로직 완결, 로컬 테스트 용이, 디버깅은 내 로그만
- 앱 스레드는 invoke 응답 대기만 함 — 이미지 바이트가 힙에 안 들어옴 (방식 0의 힙 문제 해소)
- 재배포해도 PENDING이 DB에 남아 재기동 후 자동 재개
- 추후 확장 시 디스패처의 invoke를 SQS send로 바꾸면 방식 1로 **자연 이행** 가능

**단점**:
- 앱이 내려가 있는 동안은 처리도 멈춤 (데이터는 안전, 진행만 중단 — 방식 1은 계속 돌아감)
- 페이싱·클레임·재시도 코드를 직접 작성·테스트해야 함 (방식 1에선 SQS 설정이던 것)
- Lambda 레포 배포 파이프라인 추가는 방식 1과 동일

## 4. 결론 (의견)

**이 프로젝트에는 방식 2를 권장한다.**

- 단일 EC2·프리티어·월 고정비 0원·최소 인프라 기조에 부합 (새 인프라는 Lambda 함수 1개뿐)
- 분당 5회라는 명시적 제약에는 근사(방식 1)보다 정밀 페이싱(방식 2)이 맞음
- 방식 0의 실질 문제(접수 거부·증발·429·힙)를 전부 해소하면서 복잡도 증가가 가장 작음
- 방식 1이 합리적이 되는 시점: EC2 다중 인스턴스 확장(디스패처 단일 실행 보장 붕괴),
  RDS 이전, 또는 SQS 학습·포트폴리오 가치를 우선할 때. 방식 2 → 방식 1 이행 경로가
  자연스러우므로 지금 방식 2로 시작해도 매몰비용이 없음

## 5. 다음 단계 메모

- Lambda 함수는 기존 `~/jipsamoye.image-lambda` 레포(Node.js 20 arm64 + SAM)에 추가하기로 결정
